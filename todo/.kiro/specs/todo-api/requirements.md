# Requirements Document

## Introduction

This document describes the requirements for the Todo REST API feature for the Water Tribe project. The API is built on Spring Boot 4.1.0 with Java 21, using Spring Security for session-based authentication, Spring Session with JDBC backing, and SQLite via Hibernate ORM.

The feature covers four main areas:
1. **User registration** — creating a new account with a unique username, unique email, and a securely hashed password.
2. **User authentication** — session-based login and logout via Spring Security.
3. **MainTodo CRUD** — creating, reading, updating, and deleting todo items scoped to the authenticated user.
4. **Subtask CRUD** — creating, reading, updating, and deleting subtasks linked to a parent MainTodo, also scoped to the authenticated user.

---

## Glossary

- **API**: The Spring Web MVC REST API described in this document.
- **User**: A registered account, identified by a unique username and unique email, with a BCrypt-hashed password.
- **Session**: An HTTP session managed by Spring Session, persisted to the SQLite database via JDBC.
- **MainTodo**: A top-level todo item belonging to exactly one User, with a task title, optional description, completion state, and timestamps.
- **Subtask**: A child task belonging to exactly one MainTodo, with a title, optional description, and its own completion state.
- **Registration_Service**: The component responsible for validating and persisting new User registrations.
- **Authentication_Filter**: The Spring Security filter chain component responsible for processing login and logout requests.
- **Todo_Service**: The component responsible for CRUD operations on MainTodo entities.
- **Subtask_Service**: The component responsible for CRUD operations on Subtask entities.
- **Authorization_Filter**: The Spring Security filter chain component that enforces authentication on protected endpoints.
- **BCrypt**: The password hashing algorithm used to store User passwords.
- **Principal**: The currently authenticated User whose identity is resolved from the active Session.

## Requirements

### Requirement 1: User Entity

**User Story:** As a developer, I want a well-defined User entity, so that user data is stored consistently and securely in the database.

#### Acceptance Criteria

1. THE User SHALL have a unique, non-null `id` field generated by the database as the primary key.
2. THE User SHALL have a `username` field that is non-null and unique across all Users.
3. THE User SHALL have an `email` field that is non-null and unique across all Users.
4. THE User SHALL have a `passwordHash` field that is non-null and stores the BCrypt-hashed password; the plain-text password SHALL NOT be persisted.
5. THE User SHALL have a `roles` field that stores the granted authorities used by Spring Security for authorization decisions.
6. THE User SHALL have a `createdAt` timestamp field automatically set to the current UTC time when the entity is first persisted.
7. THE User SHALL implement `UserDetails` so that Spring Security can load authentication and authorization information directly from the entity.

---

### Requirement 2: User Registration

**User Story:** As a visitor, I want to register a new account with a username, email, and password, so that I can log in and manage my todos.

#### Acceptance Criteria

1. WHEN a `POST /api/users/register` request is received with a valid username, email, and password, THE Registration_Service SHALL persist a new User with a BCrypt-hashed password and return `201 Created` with the created user's `id`, `username`, and `email`.
2. WHEN a registration request is received with a username that already exists, THE Registration_Service SHALL return `409 Conflict` with an error message identifying the duplicate field.
3. WHEN a registration request is received with an email that already exists, THE Registration_Service SHALL return `409 Conflict` with an error message identifying the duplicate field.
4. WHEN a registration request is received with a blank or missing `username`, THE Registration_Service SHALL return `400 Bad Request` with a descriptive validation error message.
5. WHEN a registration request is received with a blank or missing `email`, THE Registration_Service SHALL return `400 Bad Request` with a descriptive validation error message.
6. WHEN a registration request is received with a blank or missing `password`, THE Registration_Service SHALL return `400 Bad Request` with a descriptive validation error message.
7. WHEN a registration request is received with a `password` shorter than 8 characters, THE Registration_Service SHALL return `400 Bad Request` with a descriptive validation error message.
8. WHEN a registration request is received with a malformed `email` (not matching the standard email format), THE Registration_Service SHALL return `400 Bad Request` with a descriptive validation error message.

---

### Requirement 3: User Authentication — Login

**User Story:** As a registered user, I want to log in with my username and password, so that I receive a session that authorizes me to access my todos.

#### Acceptance Criteria

1. WHEN a `POST /api/auth/login` request is received with a correct username and password, THE Authentication_Filter SHALL authenticate the User, create a server-side Session persisted via Spring Session JDBC, set a session cookie on the response, and return `200 OK` with the authenticated user's `id` and `username`.
2. WHEN a `POST /api/auth/login` request is received with an incorrect password, THE Authentication_Filter SHALL return `401 Unauthorized` with an error message.
3. WHEN a `POST /api/auth/login` request is received with a username that does not exist, THE Authentication_Filter SHALL return `401 Unauthorized` with an error message.
4. WHEN a `POST /api/auth/login` request is received with a blank or missing `username` or `password`, THE Authentication_Filter SHALL return `400 Bad Request` with a descriptive validation error message.

---

### Requirement 4: User Authentication — Logout

**User Story:** As an authenticated user, I want to log out, so that my session is invalidated and I am no longer authorized.

#### Acceptance Criteria

1. WHEN an authenticated `POST /api/auth/logout` request is received, THE Authentication_Filter SHALL invalidate the current Session, clear the session cookie, and return `200 OK`.
2. WHEN an unauthenticated `POST /api/auth/logout` request is received, THE Authentication_Filter SHALL return `401 Unauthorized`.

---

### Requirement 5: Authorization Enforcement

**User Story:** As a system operator, I want all todo and subtask endpoints to require authentication, so that unauthenticated users cannot access or modify any data.

#### Acceptance Criteria

1. WHEN any request to `/api/todos/**` or `/api/subtasks/**` is received without a valid Session, THE Authorization_Filter SHALL return `401 Unauthorized`.
2. WHEN any authenticated request to `/api/todos/**` or `/api/subtasks/**` is received with a valid Session, THE Authorization_Filter SHALL allow the request to proceed to the appropriate handler.
3. THE API SHALL permit unauthenticated access to `POST /api/users/register`, `POST /api/auth/login`, and the Spring Security logout endpoint without requiring a valid Session.

---

### Requirement 6: MainTodo — Create

**User Story:** As an authenticated user, I want to create a new todo item, so that I can track a task I need to complete.

#### Acceptance Criteria

1. WHEN an authenticated `POST /api/todos` request is received with a valid `task` field, THE Todo_Service SHALL persist a new MainTodo associated with the Principal, set `completed` to `false`, set `createdAt` and `updatedAt` to the current time, and return `201 Created` with the full MainTodo representation.
2. WHEN an authenticated `POST /api/todos` request is received with a blank or missing `task` field, THE Todo_Service SHALL return `400 Bad Request` with a descriptive validation error message.

---

### Requirement 7: MainTodo — Read

**User Story:** As an authenticated user, I want to retrieve my todo items, so that I can review what I need to do.

#### Acceptance Criteria

1. WHEN an authenticated `GET /api/todos` request is received, THE Todo_Service SHALL return `200 OK` with a list of all MainTodos belonging to the Principal; IF the Principal has no MainTodos, THE Todo_Service SHALL return `200 OK` with an empty list.
2. WHEN an authenticated `GET /api/todos/{id}` request is received and the MainTodo with the given `id` exists and belongs to the Principal, THE Todo_Service SHALL return `200 OK` with the full MainTodo representation.
3. WHEN an authenticated `GET /api/todos/{id}` request is received and no MainTodo with the given `id` exists, THE Todo_Service SHALL return `404 Not Found`.
4. WHEN an authenticated `GET /api/todos/{id}` request is received and the MainTodo with the given `id` exists but belongs to a different User, THE Todo_Service SHALL return `403 Forbidden`.

---

### Requirement 8: MainTodo — Update

**User Story:** As an authenticated user, I want to update my todo items, so that I can change the task details or mark them complete.

#### Acceptance Criteria

1. WHEN an authenticated `PUT /api/todos/{id}` request is received with valid fields and the MainTodo belongs to the Principal, THE Todo_Service SHALL update the allowed fields (`task`, `description`, `completed`), set `updatedAt` to the current time, persist the changes, and return `200 OK` with the updated MainTodo representation.
2. WHEN an authenticated `PUT /api/todos/{id}` request is received with a blank or missing `task` field, THE Todo_Service SHALL return `400 Bad Request` with a descriptive validation error message.
3. WHEN an authenticated `PUT /api/todos/{id}` request is received and no MainTodo with the given `id` exists, THE Todo_Service SHALL return `404 Not Found`.
4. WHEN an authenticated `PUT /api/todos/{id}` request is received and the MainTodo exists but belongs to a different User, THE Todo_Service SHALL return `403 Forbidden`.

---

### Requirement 9: MainTodo — Delete

**User Story:** As an authenticated user, I want to delete a todo item, so that I can remove tasks I no longer need.

#### Acceptance Criteria

1. WHEN an authenticated `DELETE /api/todos/{id}` request is received and the MainTodo belongs to the Principal, THE Todo_Service SHALL delete the MainTodo and all of its associated Subtasks, and return `204 No Content`.
2. WHEN an authenticated `DELETE /api/todos/{id}` request is received and no MainTodo with the given `id` exists, THE Todo_Service SHALL return `404 Not Found`.
3. WHEN an authenticated `DELETE /api/todos/{id}` request is received and the MainTodo exists but belongs to a different User, THE Todo_Service SHALL return `403 Forbidden`.

---

### Requirement 10: Subtask Entity

**User Story:** As a developer, I want a well-defined Subtask entity, so that subtask data is stored consistently and linked correctly to its parent MainTodo.

#### Acceptance Criteria

1. THE Subtask SHALL have a unique, non-null `id` field generated by the database as the primary key.
2. THE Subtask SHALL have a `title` field that is non-null.
3. THE Subtask SHALL have an optional `description` field.
4. THE Subtask SHALL have a `completed` field defaulting to `false` on creation.
5. THE Subtask SHALL have a `createdAt` timestamp field automatically set to the current UTC time when the entity is first persisted.
6. THE Subtask SHALL have an `updatedAt` timestamp field automatically set to the current UTC time on both creation and every subsequent update.
7. THE Subtask SHALL have a non-null ManyToOne relationship to a MainTodo, stored as a foreign key `todo_id` in the `subtasks` table.

---

### Requirement 11: Subtask — Create

**User Story:** As an authenticated user, I want to add a subtask to one of my todos, so that I can break down a task into smaller steps.

#### Acceptance Criteria

1. WHEN an authenticated `POST /api/todos/{todoId}/subtasks` request is received with a valid `title` field and the parent MainTodo belongs to the Principal, THE Subtask_Service SHALL persist a new Subtask linked to the MainTodo, set `completed` to `false`, set `createdAt` and `updatedAt` to the current time, and return `201 Created` with the full Subtask representation.
2. WHEN an authenticated `POST /api/todos/{todoId}/subtasks` request is received with a blank or missing `title`, THE Subtask_Service SHALL return `400 Bad Request` with a descriptive validation error message.
3. WHEN an authenticated `POST /api/todos/{todoId}/subtasks` request is received and no MainTodo with the given `todoId` exists, THE Subtask_Service SHALL return `404 Not Found`.
4. WHEN an authenticated `POST /api/todos/{todoId}/subtasks` request is received and the MainTodo with the given `todoId` belongs to a different User, THE Subtask_Service SHALL return `403 Forbidden`.

---

### Requirement 12: Subtask — Read

**User Story:** As an authenticated user, I want to retrieve subtasks for one of my todos, so that I can review the steps for a task.

#### Acceptance Criteria

1. WHEN an authenticated `GET /api/todos/{todoId}/subtasks` request is received and the parent MainTodo belongs to the Principal, THE Subtask_Service SHALL return `200 OK` with a list of all Subtasks for that MainTodo; IF there are no Subtasks, THE Subtask_Service SHALL return `200 OK` with an empty list.
2. WHEN an authenticated `GET /api/todos/{todoId}/subtasks/{id}` request is received and the Subtask exists and its parent MainTodo belongs to the Principal, THE Subtask_Service SHALL return `200 OK` with the full Subtask representation.
3. WHEN an authenticated `GET /api/todos/{todoId}/subtasks/{id}` request is received and no Subtask with the given `id` exists under the given `todoId`, THE Subtask_Service SHALL return `404 Not Found`.
4. WHEN an authenticated `GET /api/todos/{todoId}/subtasks` request is received and the parent MainTodo belongs to a different User, THE Subtask_Service SHALL return `403 Forbidden`.

---

### Requirement 13: Subtask — Update

**User Story:** As an authenticated user, I want to update a subtask, so that I can change its details or mark it complete.

#### Acceptance Criteria

1. WHEN an authenticated `PUT /api/todos/{todoId}/subtasks/{id}` request is received with valid fields and the parent MainTodo belongs to the Principal, THE Subtask_Service SHALL update the allowed fields (`title`, `description`, `completed`), set `updatedAt` to the current time, persist the changes, and return `200 OK` with the updated Subtask representation.
2. WHEN an authenticated `PUT /api/todos/{todoId}/subtasks/{id}` request is received with a blank or missing `title`, THE Subtask_Service SHALL return `400 Bad Request` with a descriptive validation error message.
3. WHEN an authenticated `PUT /api/todos/{todoId}/subtasks/{id}` request is received and no Subtask with the given `id` exists under the given `todoId`, THE Subtask_Service SHALL return `404 Not Found`.
4. WHEN an authenticated `PUT /api/todos/{todoId}/subtasks/{id}` request is received and the parent MainTodo belongs to a different User, THE Subtask_Service SHALL return `403 Forbidden`.

---

### Requirement 14: Subtask — Delete

**User Story:** As an authenticated user, I want to delete a subtask, so that I can remove steps I no longer need.

#### Acceptance Criteria

1. WHEN an authenticated `DELETE /api/todos/{todoId}/subtasks/{id}` request is received and the parent MainTodo belongs to the Principal, THE Subtask_Service SHALL delete the Subtask and return `204 No Content`.
2. WHEN an authenticated `DELETE /api/todos/{todoId}/subtasks/{id}` request is received and no Subtask with the given `id` exists under the given `todoId`, THE Subtask_Service SHALL return `404 Not Found`.
3. WHEN an authenticated `DELETE /api/todos/{todoId}/subtasks/{id}` request is received and the parent MainTodo belongs to a different User, THE Subtask_Service SHALL return `403 Forbidden`.

---

### Requirement 15: Consistent Error Response Format

**User Story:** As an API consumer, I want all error responses to follow a consistent JSON structure, so that I can reliably parse and display error information.

#### Acceptance Criteria

1. WHEN THE API returns any 4xx or 5xx response, THE API SHALL include a JSON body with at minimum a `status` (integer HTTP status code) field and a `message` (human-readable string) field.
2. WHEN THE API returns a `400 Bad Request` response due to validation failures, THE API SHALL include a `errors` array in the JSON body listing each individual field-level validation error.
